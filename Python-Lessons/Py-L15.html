L15 Error Handling

Errors happen. A user enters text where you expected a number, a file doesn't exist, a network request fails. Error handling lets your program recover gracefully instead of crashing.

🛡️
try / except
Wrap risky code in a try block. If it raises an error, the except block runs instead of crashing. The program continues normally after.
Full try/except anatomy
try:← risky code goes here
    result = int(input("Enter number: "))
except ValueError:← catches specific error
    print("Not a number!")
except Exception as e:← catches anything else
    print(f"Error: {e}")
else:← runs if NO error occurred
    print(f"Got: {result}")
finally:← ALWAYS runs, error or not
    print("Done.")
Catch specific errors
Always catch the most specific exception you can. Using bare except: or except Exception: everywhere hides bugs. Catch what you expect and let the rest crash — a visible crash is better than silent wrong behavior.
Common exceptions
ValueError
wrong type/value: int("abc")
TypeError
wrong type: "a" + 1
KeyError
dict key missing
IndexError
list index out of range
ZeroDivisionError
dividing by zero
FileNotFoundError
file doesn't exist
raise — throw your own errors
You can raise errors yourself with raise ValueError("message"). Use this to enforce rules in your functions — if a caller passes invalid data, raise an error immediately rather than letting it silently cause problems later.
EAFP vs LBYL
Python favors EAFP (Easier to Ask Forgiveness than Permission) — just try it and handle errors. The alternative is LBYL (Look Before You Leap) — check everything upfront. EAFP is more Pythonic and often cleaner.
Analogy: Error handling is like a seatbelt. You don't expect to crash, but when you do, it keeps the damage controlled. finally is like turning off the engine after — it happens no matter what.
